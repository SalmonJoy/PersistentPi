## Conditions and exact grammar

A/P0 `runner-json-1` with E0 preserves M0.2 prompt, HTTP JSON mode, parser contract
and exact single-match edit semantics. B/P1 `runner-json-schema-1` uses the same
prompt and context but supplies the backend's native `format` schema: a union of
the allowed action contracts. Ollama accepted the exact schema in the saved
non-task capability probe. See [Ollama API documentation](https://github.com/ollama/ollama/blob/main/docs/api.md).
Backend constraints do not authorize paths or guarantee meaningful arguments.
Generation constraints are explicit measured factors, not adapter response repair.

C/P2 `runner-dsl-1` replaces only serialization instructions. The shared coding
restrictions, task view, registry, budgets, feedback and context truncation policy
are unchanged. Feedback remains structured data, including action/result objects.
There is no reasoning hint or chosen strategy in one condition but not another.
Grammar is case-sensitive, LF only, exactly one action:

```text
READ relative/path
VERIFY
FINISH
FINISH literal reason
EDIT relative/path
<<<<<<
literal old text
======
literal new text
>>>>>>
```

EDIT is one multi-line action, not a sequence. One final transport LF is allowed.
The LF preceding each delimiter is framing, not content; an additional LF retains
a content trailing newline. Delimiter lines are reserved. No fences, prose,
case conversion, whitespace trimming, semantic guessing or response reconstruction.
All representations become the same ActionRequest before the same Supervisor.

E1 is justified by 25 exact-context rejections, but may still fail because the
model copies placeholders or generates wrong code. E1 replaces E0's edit capability
within that condition, not adds another tool choice. Complete UTF-8 text file
replacement is limited to 8192 bytes for both input and existing file, NUL-free,
declared editable regular files only, same link/path/workspace protection and
bounded-Python AST checks. A durable pre-change checkpoint precedes atomic write.
No arbitrary Python/commands/filesystem access. DSL E1 uses `REPLACE path` plus
`<<<<<<` and `>>>>>>` framing; there is no middle delimiter. JSON E1 uses
`replace_file` with `path` and `content` strings. E0 remains available as its own
experimental condition; E1 is not a new default.

## Funnel and selection

Versioned `decision_funnel` events record all requested stages, output protocol,
edit primitive, tool, exit reason, failure family and <=500-character evidence.
Parse-valid means successful JSON decoding/DSL grammar; schema-valid means the
ActionRequest envelope; authorization also validates tool argument contracts and
declared paths. Applicability validates exact context/size/text/execution profile.
Executed counts public test invocation even when tests fail. E0 checkpoints occur
at submission; E1 also has pre-edit checkpoints, so checkpoint rates are not
direct measures of coding success. Read/finish actions legitimately stop before
verification. Format, tool-contract, coding and backend/control failures differ.
Final hidden measurements are separate events after normal Runner termination,
attributed only to the last submission of the selected checkpoint. Hidden passes
on an initial unsubmitted checkpoint are task results, not an interaction success.

Primary matrix uses budget 1, A/B/C on the four evaluation tasks. Gates for an
alternate: >=75% decisions authorized AND >=50% tasks reaching public verification.
Interrupted runs cannot qualify. Selection uses ordered verification task rate,
applicability rate, public-pass count, lower invalid rate, lower tokens; exact tie
is resolved by stable protocol ID and disclosed. Hidden pass is never a selector.
Public-only queries select no hidden columns/events. Selection is saved before
aggregated hidden results are read.

D uses the selected E0 alternate plus E1. If no E0 alternate qualifies, the
preregistered fallback is the best-ranked E0 alternate, allowing E1 to isolate
the already-justified context bottleneck without inventing a Cartesian product.
If E0 and D qualify, retain the accepted E0 condition; D only supplies a scaling
condition when E0 gates failed. Budget 1/3/5 and three budget-1 repeats on the first
two evaluation IDs run only for an accepted alternate condition. Output protocol,
edit primitive, prompts, tasks and all other budgets then stay fixed. No acceptance
means negative result and no scaling. Four tasks do not support general claims.
